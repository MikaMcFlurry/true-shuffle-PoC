# Native Home Assistant / Music Assistant bridge (NN-10)

This route is separate from Spotify Connect. A Music Assistant device advertised by Spotify remains a Spotify-controlled Connect device. The native route uses an explicitly configured local bridge and HA REST services. A public Worker does not discover or reach a private LAN automatically.

## Setup

Run `node scripts/native/ha-bridge.mjs` with Node 22+ on the HA network. Supply environment variables through a service secret store, never commit them:

- `HA_URL`: your HA origin reachable from the bridge.
- `HA_TOKEN`: HA long-lived token authorized for the configured media entities.
- `BRIDGE_TOKEN`: independently generated bearer secret, at least 32 characters.
- `BRIDGE_STATE_FILE`: durable private path for command journal, exact occurrence context and sequence; back up with permissions 0600. Preserve this file across bridge restarts.
- `BRIDGE_DEVICES`: JSON array of explicit entities and verified media URI mappings. Example shape: `[{"id":"media_player.owner_ma","name":"Music Assistant","mediaTemplate":"spotify://track/{id}","service":"music_assistant.play_media","seek":true,"pause":true}]`. Verify the actual MA version/provider accepts this URI and reports the exact identity in HA `media_content_id` before enabling the account. Some installations require an `https://open.spotify.com/track/{id}` mapping. No universal Spotify URI support is assumed.

Default listener is `127.0.0.1:8788`; `BRIDGE_HOST` and `PORT` are optional. Expose only through a reachable HTTPS endpoint, for example an owner-managed Cloudflare Tunnel with ingress targeting this listener. Keep authentication on the bridge as well as the tunnel. The bridge needs HA network access; the Worker needs the configured HTTPS bridge origin. Neither installation nor tunnel creation has been performed without the owner's live network credentials.

Set the Worker **secret** `NATIVE_BRIDGES` to JSON `{ "<spotify-account-id>": { "url": "https://your-bridge.example", "token": "<BRIDGE_TOKEN>" } }`. Bind only authorized accounts. The secret is server-side Cloudflare configuration, never returned to the browser or stored in listener history. Use a separate bridge/token/device list for accounts that must not share physical outputs. Removing an account entry revokes subsequent native calls and alarms; rotating the bridge token revokes old access. Spotify account/session/allowlist and guest restrictions still apply.

Devices appear only with an explicitly configured URI mapping, a reachable HA state and supported playback path. Native MA queue capability requires HA to advertise the `music_assistant.play_media` service. Generic HA play requires its play-media feature; pause and seek require both explicit permission and observed HA feature bits. Generic HA transports one song and does not claim an autonomous queue. UI exposes these differences.

## Continuity and trust

Ordinary native Resume uses the saved queue and observed position. The separate explicit `newQueue: true` action creates a new local queue/session and occurrence IDs while retaining history and rules. It refuses to replace an ambiguous pending command until the user cancels that command; it never invokes Spotify playback.

Commands include a durable operation ID, session ID, occurrence ID, playback epoch and order revision. The Worker journals pending transport intent before contacting the bridge. The bridge journals before the HA service effect, returns repeated acknowledged operations without repeating playback, rejects changed payloads with the same operation ID, and fences older epochs per saved session, including after switching stations. A crash between HA effect and acknowledgement leaves an explicit ambiguous pending command; it is never blindly replayed. `/api/native/cancel` cancels local intent while retaining the unfinished occurrence/checkpoint, then a deliberate Resume issues a new fenced command. This can replay that occurrence; it cannot promise an exactly-once HA service effect across a network failure.

State observations have a durable increasing sequence. Context is trusted only when HA reports the exact configured media identity for one unique queued occurrence. Duplicate identities are ambiguous and preserve the checkpoint. Missing or unrelated identity reports external playback; unavailable/idle reports disconnect. Native events never infer completion from wall time. Reported position is used directly, including a backwards seek. Unknown/unsupported seek resumes the same occurrence at zero. Spotify observations cannot overwrite a native checkpoint. Pending start/load commands require an explicit Resume or Cancel after failure; alarms never blindly send a delayed Play into unrelated music. Worker alarms observe configured native transport every 30 seconds while the app is closed; this is observed progress, not a promise of exact position through lost connectivity.

Native MA receives the ordered remaining queue through the documented list `media_id` with `enqueue: replace`. HA/MA can continue that transport while the browser is closed. Trusted sequenced observations near the held tail trigger local rule-based planning and an append-only MA `enqueue: add` command. Both local planned occurrence IDs and the bridge operation are durably journaled; retries keep the same planned tail and cannot reset the current song. Reached prefixes compact while preserving the unfinished occurrence. Appending requires the bridge to verify actual native media identity, so unrelated music is left untouched. Queued identities map back to stable True Shuffle occurrences. Generic HA single-track operation and ambiguity at repeated identities remain capability limits, not simulated support.

## Evidence and live acceptance

Official API references checked on 2026-09-30: [HA REST API](https://developers.home-assistant.io/docs/api/rest/), [HA Music Assistant integration](https://www.home-assistant.io/integrations/music_assistant/), [native MA play_media action](https://www.home-assistant.io/actions/music_assistant.play_media/). The implementation uses HA REST states and services; it does not claim compatibility with an untested MA WebSocket API/version.

`test/worker/native.test.ts` exercises authorization, origin validation, bearer/redirect handling, revocation, sanitization, observed progress and pending-controller fencing. `test/worker/native-bridge.test.ts` runs the actual Node bridge against a local HA REST fixture: native MA queue order, seek at 1:37, authenticated commands, idempotency, sequenced transition, disconnect, bridge restart and stale epochs, ambiguous failed-command recovery, append continuity and return to another saved station. `test/worker/native-rolling.test.ts` additionally executes the actual production command/observation functions against controlled HA responses for 10,000 alternating repeated-media occurrences in one playback epoch: the unfinished occurrence retains its position, reached prefixes compact, the acknowledged append journal stays bounded, and old pruned operations fail the revision fence without another provider effect. These are simulated provider fixtures, not live HA/MA evidence. Listening tests require runner permission to open local sockets.

Live acceptance remains blocked by absent owner's HA/MA instance, tunnel, native secret and test-account credentials. Required live checks: actual media mapping and identity feedback; advertised capabilities; MA native list ordering and transition; pause 1:37/disconnect/restart/resume same occurrence; device/account isolation and revocation; token rotation; unsupported seek; unrelated playback; repeated occurrence ambiguity; pending effect/ack failure recovery; native queue continuation and round boundary; and distinct MA Spotify Connect playback through Spotify. Do not mark NN-10 live PASS or release-ready from fixtures alone.
