## Confirmed request drivers

References below identify symbols at the baseline revision, since concurrent edits move line numbers.

| Path / symbol | Provider work and pressure cause |
| --- | --- |
| `hub.ts: heldPace`, `scheduleNext` | A held paused station is observed every 30 seconds for the first 3 hours since activity, every minute to 36 hours, then every 2 minutes indefinitely while Spotify still reports the paused context. A legacy continued front containing recently heard songs also retains 30-second pacing. This dominates ordinary idle traffic. |
| `hub.ts: alarm` | Every alarm calls `sync()` before jobs, including import/discovery/maintenance wakeups. Due jobs can wake again in 1–2 seconds. Thus a job wake is also a player observation even if another request just read it. |
| `store.ts: start`; `hub.ts: state` | Visible page polls state every 15 seconds; focus, visibility and online events also refresh. Hub normally reads Spotify after snapshot age exceeds 45 seconds, after a command marks `player_stale`, or at a predicted track boundary. The 15-second HTTP poll is not one Spotify request each time. |
| `hub.ts: sync` | Each sync reads player; history reads on transition/context change/backwards seek, a stop, 90 seconds of unchanged active playback, 30 minutes idle, or every `force:true` sync. `force` also enables an explicit retry for unknown operation waits. These meanings should not be accidentally coupled. |
| `hub.ts: resumeSession`, `performPlayerAction` | Resume force-syncs player and history, lists devices, then normally writes shuffle, repeat and play. Pause sends PUT first but awaits forced player/history reconciliation before acknowledging. Next force-syncs before its write. Fresh reads can therefore be repeated by commands, UI refresh and alarms. |
| `hub.ts: devices`, `pickDevice`; Home/Devices screens | Device reads have no shared response cache. Home mount, Devices screen and resume can independently enumerate the same account. A stored `ts-device` selection may outlive provider device IDs. |
| `hub.ts: peekLiked`, maintenance jobs | Active playback checks recent likes every 10 minutes; playlist refresh is due after 12 hours; liked full import after 3 days. Discovery/import/playlist work can continue during a pause. Existing shared telemetry distinguishes endpoint categories; use it to identify which maintenance work matters rather than disabling features indiscriminately. |
| `station.tsx` station detail, `history`, usage/diagnostics | Station detail polls every 15 seconds while visible but its route reads local state. History screens read SQLite. Shared usage reads Registry aggregates. These reads alone do not send Spotify requests; a display ticker need not request Spotify. |
| `SpotifyClient.token` | Token refresh is demand-driven when a request needs a token expiring in less than 120 seconds; it is not an independent hourly timer. Less request traffic can reduce renewals, but calls to the accounts service remain a separate category from Web API requests. |

`UserHub.exclusive()` serializes an account's operations. It does not by itself deduplicate sequential tab/alarm/command reads. `store.inflight` coalesces requests only within one store instance.

## Prioritized policy recommendations

1. **Share observation freshness and due time across alarms, tabs and Worker eviction.** Keep a durable successful player-read timestamp and an absolute next-observation deadline. Reuse an observation when maintenance wakes before that deadline; still run due independent jobs. Only a successful real observation advances successful-read freshness. Do not slide `nextPlayerAt` forward whenever an unrelated job runs: current `scheduleNext()` uses `now + pace`, so skipping sync without separating its deadline could postpone observations indefinitely. `lastLookAt` is in memory; paused snapshots are deliberately not rewritten for up to 3 minutes, and `setSyncState()` ignores changes solely to `lastPlayerAt`. None alone supplies durable precise freshness today.
2. **Reduce ordinary paused/background observation while keeping explicit controls prompt.** A concrete candidate for measurement is 60 seconds for the first 5 minutes, 5 minutes up to 3 hours, 15 minutes up to 36 hours, and 30 minutes thereafter. This is an engineering candidate, not an accepted product SLA or measured result. It trades request reduction for up to that much delay recognizing Spotify-side resume while the app is closed. Opening/focusing the app should obtain a fresh observation when required; commands must not wait for the background interval. A durable saved session must survive any pause length and never expire with the observation schedule.
3. **Preserve the existing sensitive observation minima.** Private playback needs its observation at 30 seconds and short subsequent checks because Spotify may omit it from recently played. Keep private-lately and private paused guards; guest-end/boundary checks; old-order checks; guarded upcoming songs; legacy recently-heard front protection; stale-command reconciliation; and track-end checks. Define these as earlier absolute deadlines than ordinary paused pacing. Do not apply a coarse global minimum interval that suppresses a 15/20/30-second sensitive observation.
4. **Keep playing observation aligned to real boundaries.** Retain provider-observed duration/progress scheduling and the longer-song fallback. A local one-second progress display must never write checkpoints, declare completion, advance an occurrence or generate provider reads. Visible ordinary playback can reuse 45–60-second observations with a boundary exception, but special guest/private/guard checks remain independent. A boundary deadline is based on the original provider observation time, not the most recent cache read time.
5. **Separate command observation from history/maintenance.** A resume preflight can read player and checkpoint the latest observed position without awaiting unrelated likes/history or automatic playback repair. A successfully acknowledged pause can schedule durable observation immediately after the PUT. Preserve a durable deferred-history marker until a history read succeeds; the first full sync must consume it. Do not simply drop a transition's history read because a player-only preflight has overwritten the previous snapshot. Keep backwards seeks, repeated-track ambiguity, guest/private bookkeeping and failed-observation fallback. Fresh memory is still required before planning a new order.
6. **Use bounded account-owned device caching.** A successful current player read already supplies its active device. Automatic selection may reuse that nonrestricted device if the observation is fresh; cache successful device enumeration briefly (a proposed 60 seconds), including a shorter negative cache for an empty response. Explicit selection/manual refresh, changed observed device, stale ID and actual `no_device`/restricted failure should invalidate the relevant cache. Do not create a cache-refresh timer. A selected device should not silently fall back to another speaker merely because it disappeared. An actual failure may justify one bounded rediscovery/retry where intent still permits it; do not loop transport writes.
7. **Avoid redundant configuration writes only from confirmed state.** Skip shuffle/repeat writes only if a fresh observation establishes the desired values for the same target device. `repeat_state` exists in Spotify's response but the baseline `PlayerObservation` does not carry it. Unknown/stale/other-device repeat state does not justify skipping `setRepeat("off")`. A cache hit is not proof that a previously failed write recovered.

An appropriate minimal structure is `nextObservationAt` independent of `nextJobAt`, with `alarmAt = min(nextObservationAt, nextJobAt, guest/private/command deadlines)`. `alarm()` synchronizes when an observation is due or a dependent job needs freshness, then processes jobs. This is a compatibility direction, not a drop-in patch or a tested implementation.

### Dependent jobs and history caveats

- `stepDeck()` already refreshes a stale player before rewriting and calls `freshenMemory()` before planning. Preserve both checks.
- `stepExtend()` currently does **not** make those freshness checks before planning/trimming. It relies on `alarm()` syncing first. Removing unconditional alarm sync without replacing this dependency can plan from stale memory or trim using an old current index. Preserve a fresh observation for extend, or add an explicit equivalent guard before publication; unfinished occurrence and entry IDs must remain intact.
- Normal history reads request one page of at most 50 entries. `recordPlays()` warns when a full page of new plays may have lost older entries; it does not paginate catch-up. Do not claim lossless arbitrary catch-up after hours of background suppression. Keep independently due history no later than the existing 30-minute idle policy, and retain active-transition reads. Even 30 minutes can exceed 50 short qualifying tracks; this existing limitation requires separate bounded pagination work if stronger guarantees are desired.
- Successful player reads cannot clear a history hold, or vice versa. Player failure with a confirmed operation hold must still permit independently due history. Unknown-duration holds must not become automatic probing loops.

## Official Spotify device and quota semantics

Primary pages fetched read-only on 2026-10-01:

- [Available devices](https://developer.spotify.com/documentation/web-api/reference/get-a-users-available-devices): `is_active` means currently active; `is_restricted: true` means Web API commands are not accepted. These are different properties. Some models are not supported/listed. Device IDs are persistent only to some extent and cached IDs should periodically be cleared/refetched as necessary. An inactive entry is not by itself proof of a restriction or an error.
- [Playback state](https://developer.spotify.com/documentation/web-api/reference/get-information-about-the-users-current-playback): returns current playback, progress and the active device; 204 is a documented response. A missing observation is not proof that the durable unfinished occurrence completed.
- [Start/resume playback](https://developer.spotify.com/documentation/web-api/reference/start-a-users-playback): `device_id` targets that device; without it the currently active device is targeted. Premium is required. Spotify explicitly warns that execution order is not guaranteed when combined with other Player API endpoints; successful HTTP responses do not prove instantaneous device reconciliation.
- [Transfer playback](https://developer.spotify.com/documentation/web-api/reference/transfer-a-users-playback): transfers to one device, with optional `play`; only one ID is supported. `play: false` or omission preserves playback state. Transfer is an available command, not evidence that it is needed to fix the owner's iPhone.
- [Recently played](https://developer.spotify.com/documentation/web-api/reference/get-recently-played): maximum page size is 50; `after` and `before` are exclusive cursor choices. This supports the catch-up caveat above.
- [Rate limits](https://developer.spotify.com/documentation/web-api/concepts/rate-limits) distinguishes the rolling 30-second rate limit and other endpoint limits; [quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes) separately documents development quota across one developer account, changing endpoint bucket groupings and limits. Neither page provides this app's remaining allowance. Application operation holds must not be described as Spotify's proven bucket topology.

The owner's active-iPhone symptom remains unreproduced by this audit. The exact failed HTTP method/operation, status/reason, observed device state and outcome after a fresh device selection are needed to identify the cause. These primary sources do not establish an iOS wake guarantee, reliable control of a suspended/offline Spotify app, or successful physical-device recovery. No cache, retry policy or UI change should be called an iPhone fix without that provider/device evidence.
