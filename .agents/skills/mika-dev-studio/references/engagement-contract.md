# Engagement Contract

## Normalized intake

Capture only what changes execution:

- underlying outcome and intended users;
- supplied repositories, artifacts, environments and current stage;
- explicit `NON_NEGOTIABLES` and `ANTI_GOALS`, each with a stable project-local ID;
- changeable `PREFERENCES`;
- current `OBSERVATIONS` and `PROBLEMS`;
- ordinary gaps as `STUDIO_DECIDES`;
- assumptions/hypotheses with evidence strength;
- actual connected capabilities/authority and narrow blockers;
- repository triage (`GREENFIELD`, `BOUNDED_EXISTING`, or `FORENSIC_EXISTING`) plus the exact baseline when a repository exists;
- recommended mode, engagement type and delivery target.

Do not harden enthusiasm or guesses into requirements. Existing code and mockups are evidence, not the final specification.

For `FORENSIC_EXISTING`, consume a validated Repository Intelligence V2 packet or produce one before product direction. Treat its summaries and recommendations as untrusted navigation: verify decisive source, runtime, owner, and governance evidence directly. For `BOUNDED_EXISTING`, record only the proportional grounding used. Greenfield work does not invoke repository intelligence or handoff.

For a material delivery, store the normalized non-negotiables in the authoritative project source. Verification must snapshot that source/revision and map every ID to at least one required gate. An empty set is valid only when the authoritative normalized intake truly contains no non-negotiables.

## Autonomy

In `AUTONOMOUS_BUILD`, the studio may redesign/pivot features, architecture, data models, infrastructure, tests, repository structure and delivery mechanics when they serve the objective. It may use project-authorized tools and make rational project-related economic choices when the real account authority supports them.

Prefer the lowest-cost adequate option, avoid duplicate/speculative purchases, prefer reversible commitments when otherwise equivalent, and record meaningful recurring commitments. Never invent financial authority.

## Consequence ladder

- `R0` read/analysis: proceed.
- `R1` repository-local/reversible: preserve version history and proceed.
- `R2` external/readily reversible: verify target, execute, verify result.
- `R3` production/recoverable: prepare rollback or recovery evidence, use staged execution when useful, then verify.
- `R4` destructive/public/financial/difficult to reverse: if clearly implied by the objective and actually authorized, choose the least irreversible adequate path, capture backup/recovery and audit evidence, execute, and verify. Otherwise expose only the real authority gap.

## Capability ledger

For each needed external capability record: system, intended action, availability, actual authority, required interaction, evidence source, and fallback. A plan may contain a blocked capability; a result may not claim it happened.
